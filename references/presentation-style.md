# 로고와 이미지 중심 발표 제작 원칙

이 문서는 AutoPets 발표를 만들며 사용자가 반복해서 요청한 표현 방식과 수정 기준을 다른 발표에 적용하기 위한 선택형 스타일이다. 목표는 **청중이 무엇을 만드는지 이해하고, 왜 그렇게 결정했는지 납득하게 하는 것**이다. 사용자가 같은 스타일을 요청할 때 적용하고, 새 프로젝트의 목적·브랜드·발표 방식이 다르면 그 요청을 우선한다.

## 먼저 적용할 핵심

1. 처음 듣는 사람을 기준으로 작품을 한 문장으로 설명한다. 기능 목록보다 문제와 결정 근거를 연결한다.
2. 화면은 발표 대본이 아니다. 제목 한 문장과 의미 구분에 꼭 필요한 라벨을 남기고, 긴 설명은 말로 전달한다.
3. 흰 배경·여백·검정 글자·제한된 강조색을 기본 스타일로 삼는다. 색과 수치는 이번 예시의 선택이며 모든 발표에 강제하지 않는다.
4. 브랜드를 알아보는 것이 중요하면 실제 로고를 쓴다. 일반 아이콘이나 이름만으로 대체하지 않는다.
5. 로고는 장식보다 설명의 역할을 맡는다. 위치·크기·연결·이동이 관계와 변화를 보여줘야 한다.
6. 한 장면은 하나의 중심 메시지 또는 행동에 집중한다. 애니메이션이 많아도 읽을 거리와 선택 부담은 늘리지 않는다.
7. 발표 조작은 화면 어디든 클릭→연출→멈춤→다음 클릭으로 단순화한다. 클릭 대상을 찾게 하지 않는다.
8. 앞 장면의 객체를 다음 장면으로 가져와 연속성을 만든다. 필요하면 여러 슬라이드가 하나의 화면처럼 이어져도 된다.
9. 서로 다른 개념에는 서로 다른 시각 표현을 배정한다. 비교하지 않는 속성은 고정한다.
10. 캐릭터가 필요하다면 라벨뿐 아니라 외형·소품·행동으로 역할을 읽게 한다. 얼굴과 실제 작업 화면을 가리지 않는다.
11. 조사·가설·콘셉트·진행 상태·검증 결과를 구분한다. 설득을 위해 수치나 효율을 만들어내지 않는다.
12. 원본·동작·선명도를 보존하면서 용량을 줄이고, 다른 PC에서 인터넷 없이 발표할 수 있는지 확인한다.

## 문구를 얼마나 지울 것인가

삭제할 후보는 반복 설명, 긴 부제, 발표자가 말할 대본, 클릭 안내, 메모·전체화면 버튼, “연출 중” 같은 관리 상태 문구다. 제목·짧은 역할명·현재/다음 단계·모델과 추론의 구분·추천 이유·숫자의 단위처럼 지우면 뜻이 달라지는 정보는 남긴다. 조작 기능 자체를 없애라는 의미는 아니다.

출처를 발표자 메모에 옮기자는 초기 지시는 이후 “발표 메모는 필요없어”로 바뀌었다. 이 프로젝트에서는 발표 화면에 메모를 두지 않되 근거를 별도로 보존한다. 새 발표가 대본이나 발표자 메모를 요구하면 그 요청을 따른다.

## 로고 플레이를 설계하는 방법

| 전달할 뜻 | 시각적 구성 | 피할 구성 |
| --- | --- | --- |
| 어떤 도구인지 | 실제 브랜드 로고와 짧은 이름 | 브랜드와 무관한 범용 아이콘 |
| 무엇이 연결되는지 | 요청에서 UI, 기술 요소로 이어지는 선 | 로고만 의미 없이 나열 |
| 선택지가 너무 많음 | 로고 누적·항목 타이핑·확인된 지표 | 처음부터 끝까지 산만한 화면 |
| 나에게 필요한 도구 | 많은 요소에서 하나를 선택해 수렴 | 이유 없이 추천만 등장 |
| 같은 도구를 사용함 | 이전 장면의 블록을 가져와 소품으로 변환 | 같은 로고가 끊겨 새로 등장 |
| 역할이 달라짐 | 동일 캐릭터의 복장·도구·행동 변화 | 매 단계마다 다른 캐릭터 생성 |

Figma 블록이 로고 더미에서 빠져나와 구르미의 장난감이 되는 최근 수정은 “정보의 나열→내가 쓸 도구”라는 관계를 이동으로 보여준 사례다. 베레모·스타일러스·화면 설계 보드는 “UI 디자이너”라는 역할을 캐릭터 자체로 설명한다. 이는 특정 소품을 모든 발표에 붙이라는 규칙이 아니다.

## 일부러 복잡하게 보여주는 예외

“세부 문구를 줄여라”와 “현학적인 설명을 길게 보여줘”는 동시에 성립한다. 복잡한 기술을 다루기 어렵다는 점을 체감시키는 앞 장면에서만 정확한 용어와 설정을 빽빽하게 보여준다. 바로 다음 장면에서는 같은 내용을 캐릭터·로고·짧은 설명으로 이해하게 한다.

예시는 Ponytail 기술 설명→코드를 정리하는 시니어 개발자 상징, AI 컨텍스트·Plan Mode·모델·스킬 설명→친숙한 구르미, 도구와 스킬의 과잉→나에게 맞는 추천이다. 앞 장면과 뒤 장면의 의미가 대응해야 하며, 어려워 보이려고 가짜 전문 용어나 검증되지 않은 효율을 덧붙이지 않는다.

## 발표자가 조작을 의식하지 않게

빈 곳·글자·사진·캐릭터를 눌러도 같은 다음 단계로 진행한다. 짧은 질문·응답·추천처럼 한 논리 흐름은 한 클릭 안에서 순서대로 보여준 뒤 멈춘다. 영상처럼 전체 발표를 계속 자동 진행하지 않는다.

연출 중 중복 다음 입력은 무시한다. 이전 이동이나 주소 직접 진입은 진행 중인 타이머·동작을 취소하고 올바른 장면으로 복구한다. 모션 줄이기에서는 최종 정보가 즉시 보이게 한다. 단순 시각 수정에 클릭 단계를 추가하지 않는다.

## 사용자의 프롬프트 방식

사용자는 다음 요소를 짧은 후속 요청으로 점진적으로 구체화했다. 매번 긴 요구서가 필요한 방식은 아니며, 이미 합의한 배경과 범위는 계속 유지한다.

| 요청의 요소 | 실제 요청에서 보이는 방식 | 다른 발표에 쓸 문장 |
| --- | --- | --- |
| 대상 지정 | 9/3페이지, 문제원인 파트, 마지막 수정안 | “[장면]에서…” |
| 문제 지적 | 두 개가 똑같아서 구분이 안 감 | “[요소 A/B]가 구분되지 않아.” |
| 인상과 목표 | 깔끔하게, 직관적으로, 로고 플레이 | “[청중]이 [의미]를 바로 이해하게 해줘.” |
| 전환 관계 | 현학적이고 어려움→쉽고 직관적 | “[앞 상태]에서 [뒤 상태]로 이어줘.” |
| 보존 범위 | 기존 페이지는 놔두고, 그냥 PPT만 | “[유지 대상]은 그대로 두고 여기만 바꿔줘.” |
| 구체화 | EX FIGMA, 사진 둘 다, 팀명 추가 | “[실제 자산/브랜드/이름]을 사용해줘.” |
| 완료 기준 | 다른 컴퓨터 발표, 용량 검수 | “[오프라인/크기/이동]까지 확인해줘.” |

재사용 수정 틀:

> [대상 장면]에서 [현재 문제]가 있어. [원하는 변화]로 바꾸고 [앞뒤 장면 연결]을 살려줘. [유지할 내용·기능·작업 범위]는 그대로 두고, [가독성·동작·용량 등의 기준]으로 확인해줘.

## 충돌하는 요청을 처리하는 기준

- 모델과 추론을 모두 크기로 표현하던 안은 **모델=크기, 추론=동일 크기의 집중 게이지**로 대체됐다.
- 메모 제거는 초기의 출처 표시 위치를 바꾼 요청이다. 문구 축소 원칙이나 근거 보존을 취소한 것이 아니다.
- 새 사진 강조는 이전 두 사진을 넣으라는 요청의 보완이다. 이전 자료를 삭제하라는 뜻이 아니다.
- 학과 역할의 타원 연출 거절은 해당 장면의 선택이다. 모든 원형 시각화를 금지하지 않는다.
- 처음 9장이라는 계획은 추가 장면 요청으로 확대됐다. 장수를 고정하지 말고 시간 배분을 다시 확인한다.
- “PPT만 수정”은 당시 구르미 장면 편집 범위를 제한했다. 스킬·저장소·외부 배포를 자동 갱신하지 않는다.

## 검수와 토큰 효율

먼저 장면 목록과 자산 메타데이터를 읽고 수정할 조각만 불러온다. 대형 독립 HTML의 Base64, 전체 변경 기록, 모든 참고 파일을 반복해서 읽지 않는다. 이번 문서로 기준을 잡은 후 필요한 항목만 [전체 목록](presentation-request-catalog.md)이나 [JSON](../data/presentation-preferences.json)에서 찾는다.

장면 수정은 그 장면부터 확인하고 공통 스타일·동작이 바뀌면 영향 범위를 넓힌다. 최종 배포 검수는 [quality-checks.md](quality-checks.md)를 사용한다. 읽은 파일·본문량을 실제 토큰 청구량과 혼동하지 않는다.

## 프로젝트에만 해당하는 값

AutoPets의 5분 발표, 9/14/20장 버전, 구르미·구르미귀여워, 모델 이름, Light/Medium/High, Figma 장난감, MCP·하네스·진화 계획은 사례다. 15MiB 목표·20MiB 조사 기준, 사진 WebP 품질90·1350×1800도 이 사례의 출발점이다. 새 발표의 내용이나 환경에 맞게 바꾼다.

Ponytail 효율, 모델 라우팅 결과, GitHub 스타, 스킬 설치 수는 다시 사용할 때 출처·날짜·조건을 확인한다. 당시의 Sol Light 기본값 정정이나 특정 학과에 관한 관점은 보편적인 제품 사실·학과 평가가 아니다.

새 발표의 시작과 수정에 쓸 완성형 문장은 [상황별 프롬프트](presentation-prompt-pack.md)에 있다. [검색 화면](../prompt-library.html)은 원문 발췌·의도·재사용 문장·확인 기준을 한 항목씩 보여준다.
