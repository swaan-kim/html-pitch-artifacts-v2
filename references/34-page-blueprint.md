# 34-page Pitch Blueprint

This is the full reusable sequence modeled on the final Follome deck. It preserves the rhythm and information hierarchy without carrying Follome-specific claims or branding.

| # | Stable page ID | Communication job | Layout / tone |
|---:|---|---|---|
| 1 | `cover` | Product promise in one sentence | Cover / dark |
| 2 | `problem-impact` | Show direct and secondary victims | Contrast / dark |
| 3 | `problem-evidence` | Prove urgency with one sourced number | Metric / dark |
| 4 | `status-quo-limit` | Explain why the current system fails | Steps / dark |
| 5 | `problem-intensity` | Show why category alone is insufficient | Contrast / dark |
| 6 | `problem-context` | Show why context changes meaning | Contrast / dark |
| 7 | `platform-gap` | Convert the gap into an opportunity | Contrast / dark |
| 8 | `setup-comparison` | Make initial setup tangible | Contrast / light |
| 9 | `fast-calibration` | Turn choices into a starting profile | Steps / light |
| 10 | `training-data` | Establish relevant data credibility | Metric / light |
| 11 | `context-inference` | Demonstrate contextual inference | Contrast / light |
| 12 | `hybrid-decision` | Combine model and user standard | Steps / light |
| 13 | `product-start` | Show the first product state | Product / light |
| 14 | `product-content` | Show the work-item overview | Product / light |
| 15 | `product-action` | Show the primary action | Product / light |
| 16 | `product-history` | Show traceability and recovery | Product / light |
| 17 | `one-item-flow` | Explain one end-to-end path | Steps / dark |
| 18 | `ax-paradox` | Reject automation that creates more work | Contrast / dark |
| 19 | `trusted-operation` | Keep only necessary human judgment | Steps / dark |
| 20 | `model-strategy` | Explain the compounding product asset | Contrast / dark |
| 21 | `team-business` | Prove customer and distribution insight | Team / light |
| 22 | `first-customer` | Define the reachable beachhead | Growth / light |
| 23 | `go-to-market` | Show the first measurable funnel | Growth / light |
| 24 | `market-expansion` | Show staged market expansion | Growth / light |
| 25 | `differentiation` | Compare with current operating alternatives | Contrast / light |
| 26 | `pricing` | Define the exact paid unit | Metric / dark |
| 27 | `unit-economics` | Connect price to variable cost | Metric / dark |
| 28 | `team-development` | Prove continued delivery capability | Team / light |
| 29 | `api-contract` | Reduce the product to key API inputs/outputs | API / light |
| 30 | `frontend-architecture` | Show UI-to-server integration | Architecture / dark |
| 31 | `backend-architecture` | Show sync and background processing | Architecture / dark |
| 32 | `database-architecture` | Show decision and feedback traceability | Architecture / dark |
| 33 | `purpose` | State three changes the product exists for | Purpose / light |
| 34 | `closing` | Resolve the opening and request action | Closing / light |

The page count is a framework, not permission to invent evidence. If a contract has no meaningful proof, mark it as a gap and gather evidence before finalizing the page.
