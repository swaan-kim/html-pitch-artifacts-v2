# 발표 제작 요청 전체 목록

이 대화에 제공된 사용자 요청과 사용자 승인 계획, 기존 25건 사례집. 다른 채팅 전체나 확인하지 않은 실행 기록은 포함했다고 주장하지 않는다.

원문은 관련 부분의 발췌이며 중복 메시지를 합쳤다. 일부 공백·줄바꿈·링크 표기만 읽기 좋게 정리했다. 긴 계획의 세부 내용은 note에서 요약하고 원문과 구분했다.

정리일: 2026-09-30. 12개 분류, 64개 재사용 지침, 36개 출처 묶음. 아래 지침과 프롬프트는 원문을 일반화한 결과이며 구현 완료 증거가 아니다.

## 목적과 맥락

### P01 청중의 이해를 성공 기준으로

적용 범위: 일반 원칙

처음 듣는 사람이 무엇을 만들고 왜 결정했는지 설명할 수 있어야 한다.

출처: S06

재사용 프롬프트:

> 발표 후 청중이 [만드는 것]과 [그 선택의 이유]를 이해하도록 구성해줘. 기능 나열보다 문제·결정·근거의 연결을 우선해줘.

확인 기준: 작품 한 문장과 결정 근거를 각각 말할 수 있는가?

### P02 현재 프로젝트부터 확인

적용 범위: 일반 원칙

프로젝트 폴더와 최신 결정으로 맥락을 확인하고 옛 주제는 구분한다.

출처: S02, S03

재사용 프롬프트:

> 먼저 [프로젝트]의 현재 목표와 진행 상태를 확인해줘. 이전 주제는 과거 자료로 분리하고 이번 발표에 섞지 마.

확인 기준: 최신 주제와 옛 기획이 뒤섞이지 않았는가?

### P03 정보를 받기 전 제작하지 않기

적용 범위: 일반 원칙

사용자가 자료 공유와 계획을 요청한 단계에서는 그 단계를 존중한다.

출처: S01, S26

재사용 프롬프트:

> 지금은 [목차/계획]까지만 정리해줘. 다음에 주는 자료를 반영한 뒤 제작으로 넘어가자.

확인 기준: 현재 요청이 자료 파악·계획·구현 중 무엇인지 맞췄는가?

예외와 주의: 이미 구현을 요청했다면 같은 승인을 다시 요구하지 않는다.

### P04 시간에 맞춰 분량을 정하기

적용 범위: 일반 원칙

장수보다 발표 시간과 말할 내용을 기준으로 흐름을 설계한다.

출처: S06, S12, S23

재사용 프롬프트:

> [시간]분 발표야. 장면별 시간을 배분하고 전환 여유를 남겨줘. 장수는 고정하지 말고 내용에 맞춰줘.

확인 기준: 전체 시간과 전환 시간이 합산되는가?

적용 예시: 5분 발표, 당시 4분50초 내용+10초 전환. 9→14→20장으로 확장된 사례이며 20장은 기본값 아님.

### P05 전체 발표와 제품 목업 구분

적용 범위: 일반 원칙

제품 이미지 요청이 전체 발표 요청으로 확대되면 결과물도 전체 서사로 바꾼다.

출처: S07, S08, S09

재사용 프롬프트:

> 제품 화면 몇 장에 그치지 말고 [전체 목차]를 포함한 HTML 발표를 만들어줘. 제품 목업은 그 안의 사용 시나리오로 넣어줘.

확인 기준: 소개·문제·근거·제작 계획·마무리가 빠지지 않았는가?

기존 사례집 연결: change-01


## 구성과 설득

### P06 작품 한 문장으로 시작

적용 범위: 일반 원칙

기능 이름보다 대상·하는 일·사용자 이익을 한 문장으로 압축한다.

재사용 프롬프트:

> [누구]가 [어려움]을 해결하도록 [경험]을 제공하는 작품이라는 한 문장부터 잡아줘.

확인 기준: 한 문장만 들어도 제작 대상이 분명한가?

출처: S06, S12

재사용 프롬프트:

> 조사 내용을 나열하지 말고 [관찰] → [문제] → [우리의 결정] 순서로 정리해줘.

확인 기준: 각 핵심 결정에 조사나 경험 근거가 붙는가?

### P08 문제 헤드라인과 사례 분리

적용 범위: 일반 원칙

문제의 요약 문장과 구체적 사례를 나누어 이해를 돕는다.

출처: S11, S12

재사용 프롬프트:

> 핵심 문제는 한 문장으로, 실제 사례는 짧은 카드나 원본 이미지로 따로 보여줘.

확인 기준: 문제 한 문장이 사례를 과장하지 않는가?

적용 예시: 무엇을 물어야 할지도 모르는 상황 → 선택 기준·스킬 활용·답 검증의 어려움.

### P09 원본 메모를 문제 원인으로 분류

적용 범위: 일반 원칙

발표자가 설명할 자료는 원본 이미지와 짧은 분류만으로 구성한다.

출처: S17

재사용 프롬프트:

> 첨부 메모 이미지를 [문제 유형]별로 묶어줘. 내가 읽고 설명할 테니 옆에 긴 요약을 다시 쓰지 마.

확인 기준: 메모 글자가 읽히고 출처별 내용이 혼동되지 않는가?

기존 사례집 연결: change-09

### P10 필요성 다음에 구조 설명

적용 범위: 일반 원칙

왜 필요한지를 먼저 설득하고 뒤에서 기술 연결을 보여준다.

출처: S25, S14

재사용 프롬프트:

> [기능]의 필요성을 뒷받침하는 근거를 한 장에 먼저 넣고, 그 다음 아키텍처로 이어줘.

확인 기준: 기술 구조에 앞서 필요성이 이해되는가?

적용 예시: 모델 라우팅 필요성 → 펫 뒤의 프롬프트·라우팅·스킬·MCP 연결.

기존 사례집 연결: change-21

### P11 개인 관점을 마무리 서사로

적용 범위: 선택 가능한 서사 패턴

발표자의 대본을 그대로 붙이지 않고 공간·로고·전환으로 요약한다.

출처: S23, S28

재사용 프롬프트:

> 아래는 대본이야. 문장 전체를 화면에 넣지 말고 [양쪽 전문성] → [변화] → [우리의 역할]로 장면을 만들어줘.

확인 기준: 개인 관점·비유를 객관적 우열이나 역사적 사실로 단정하지 않는가?

적용 예시: 좌 컴공·우 미대 → AI로 역할 확장 → 글미의 기술 적용 → 익숙한 서비스 → 도구 제작 지향.

기존 사례집 연결: change-23


## 문구와 정보량

### P12 세부 문구를 대부분 덜어내기

적용 범위: 사용자 선호 스타일

화면에는 핵심 문장과 이미지가 남고, 긴 설명은 말로 전달한다.

출처: S01, S08, S14

재사용 프롬프트:

> 세부 문구는 어지간하면 삭제해줘. 제목 한 문장, 꼭 필요한 라벨, 이미지·로고 중심으로 남기고 말로 설명할 내용은 화면에서 빼줘.

확인 기준: 각 문구를 지워도 이해되면 삭제했는가?

예외와 주의: 의미 구분에 필요한 상태·단위·짧은 추천 이유는 남긴다. 모든 슬라이드의 글자를 0개로 만드는 규칙이 아니다.

기존 사례집 연결: change-06

### P13 발표 조작 안내는 화면에서 숨기기

적용 범위: 사용자 선호 스타일

아무 곳이나 클릭·메모·전체화면·연출 중 같은 관리 문구를 화면에서 제거한다.

출처: S14

재사용 프롬프트:

> 하단의 클릭 안내·전체화면·메모 버튼과 연출 중 문구를 발표 화면에서 숨겨줘. 필요한 조작은 키보드나 숨겨진 도움말로 유지해줘.

확인 기준: 안내 문구가 핵심 내용과 시선을 경쟁하지 않는가?

기존 사례집 연결: change-06

### P14 메모 요청의 최신 상태 반영

적용 범위: 이 프로젝트의 최종 요청

출처를 메모로 옮기려던 초기 요청 뒤에 발표 메모 불필요라는 정정이 왔다.

출처: S14, S15

재사용 프롬프트:

> 이번 발표에는 발표자 메모가 필요 없어. 출처와 검수 근거는 별도 자료로 보존하고 발표 화면에서는 빼줘.

확인 기준: 메모 제거가 출처 삭제로 이어지지 않았는가?

예외와 주의: 다른 발표에서 대본·메모를 요청하면 제공한다. 새 발표에 메모 금지를 강제하지 않는다.

기존 사례집 연결: change-07

### P15 원문과 요약을 구별하기

적용 범위: 일반 원칙

원본 이미지는 그대로, 재작성한 사례는 요약으로 표시한다.

출처: S12, S17

재사용 프롬프트:

> 인터뷰를 요약할 때 직접 인용처럼 따옴표를 붙이지 말고, 실명 없이 상황과 어려움만 보여줘. 원문 이미지는 요약과 구별해줘.

확인 기준: 창작한 문장이 실제 인터뷰 발언처럼 보이지 않는가?

### P16 미완성보다 현재 하는 일을 구체적으로

적용 범위: 일반 원칙

현재 수행 중인 조사·테스트를 정확한 작업 이름으로 표현한다.

출처: S14

재사용 프롬프트:

확인 기준: 진행 상태를 포장해 완료·효과 검증으로 과장하지 않았는가?

적용 예시: ChatGPT Web 작동 환경 파악 및 벤치마킹 테스트 구축 중.

## 이미지와 로고

출처: S01, S08

재사용 프롬프트:

확인 기준: 색·테두리·설명이 이미지보다 강하지 않은가?

예외와 주의: 브랜드 가이드나 새 요청이 있으면 그 기준을 우선한다. 모든 PPT에 흰색·초록을 강제하지 않는다.

### P18 로고 플레이를 중심 언어로

확인 기준: 로고의 위치와 동작이 의미를 갖는가, 단순 장식으로 흩어지지 않았는가?

### P19 브랜드 로고를 임의 아이콘으로 대체하지 않기

확인 기준: 로고가 잘리지 않고 브랜드를 즉시 알아볼 수 있는가?

적용 예시: MCP를 막연한 플러그 모양으로만 그리지 않고 Figma 로고 장난감으로 표현.

### P20 복잡한 설명을 의도적으로 체감시키기

확인 기준: 앞의 기술 요소가 뒤의 쉬운 표현과 대응하는가?

## 이번 사례에만 해당하는 제품 화면 세부값

다음은 일반 디자인 규칙이 아닌 AutoPets 기획 맥락이다. 새 발표에 복사할 때 제품과 사용자 상황에 맞춰 바꾼다.

- MVP의 4장: 펫 선택→설정→계획 확인→실행. 16:9, 같은 검은 고양이, 작은 MVP 콘셉트 표시, 오른쪽 위 내 펫/라이브러리로 돌아가는 집 버튼.
- 선택 화면: 알뜰 너구리·꼼꼼 고양이·집중 호랑이, 고양이 선택 상태, 성향 한 줄·대표 스킬, 대상 채팅 학과 행사 웹페이지, 설정하기 버튼.
- 설정 화면: 웹페이지 제작(요구사항 정리·화면 구현·결과 점검), 계획 Astra·추론 높음→실행 Luna·추론 보통, 계획을 확인한 뒤 실행, 저장하고 이 채팅에 부르기, 상세 모델 변경 입구. 성능 점수·절약률을 넣지 않는 설정 예시.
- 계획 화면: 행사 소개·일정 구성, 신청 버튼이 있는 화면 제작, 모바일·동작 확인의 3단계. 수정하기/이 계획으로 시작 버튼. 실행 화면: 웹페이지 만드는 중, 실행 Luna, 계획 확인→화면 제작→결과 확인, 작업으로 돌아가기.
- 역할 라이브러리: UI UX Pro Max 기반 UI 디자이너 고양이, Ponytail 기반 코드 정리 포니, 역할 템플릿인 리서처 부엉이·문서 편집자 토끼. 실제 스킬 설치·연동 완료 주장 없음.
- 추천 대화: 어떤 결과를 만들고 싶어요?→웹페이지요. 어디부터 도움이 필요해요?→처음이라 잘 모르겠어요. UI 디자이너 추천→목적과 화면 구성부터 정리→누가 보는 페이지인지 확인.
- 비교 의미: 모델은 몸 크기, 추론은 같은 크기에서 3칸 집중 게이지. 모델·추론·스킬 효과를 분리. MCP는 실제 브랜드 장난감, 관련 작업은 같은 종류의 역할별 펫·하네스, 꾸미기·진화는 확장 계획.
- 개발 진행 표는 설치부터 배포 검증까지 15개 구간의 계획이다. 모든 항목이 구현됐다는 근거가 아니다.
- 후반 학과 서사는 발표자의 자아 정의와 지향점이다. YouTube·Netflix·Adobe·Figma는 복잡한 기술을 쓰기 쉬운 도구로 설명하는 예시이며 일반적 우열이나 회사 탄생 원인의 확정 근거가 아니다.
- 이번 수정 이력은 새 발표에 펫을 반드시 넣으라는 지시도, 기존 20장 구성·초록색을 그대로 써야 한다는 지시도 아니다.
